# 12.47 one-time maintenance control — local proof, not production authorization

This procedure is **not authorized for production execution**. The stopped rollout remains stopped. It uses Vercel All Deployments protection for ordinary HTTP traffic plus a temporary PostgreSQL `public` schema `USAGE` restriction for the Project Local `anon` and `authenticated` application roles. It does not create a product maintenance feature or change any 12.47 migration.

## Scope and local evidence

On a fresh local Supabase 2.111.0 database through `20260922150000`, there were 26 public tables and 72 public functions. `anon` and `authenticated` had zero effective direct INSERT/UPDATE/DELETE/TRUNCATE privileges on those tables. `anon` could execute 10 reviewed functions; `authenticated` could execute 57 (the 10 anonymous functions plus 47 authenticated-only functions). `service_role` retained effective writes on all 26 tables and EXECUTE on 57 functions; none of the 15 internal functions was granted to it. The application uses the public anon key plus Supabase Auth sessions, not a service-role runtime client. The seven owner-observed Vercel Production variable names did not include a service-role key. Repository migrations define no `pg_cron` or Auth-user trigger that writes Project Local operational tables. This source review cannot exclude an external holder of the service-role key, a direct `postgres` connection, or an unlisted provider job; the operator must confirm those writers are idle before live use.

The local `public` schema had explicit `USAGE` for PUBLIC, `anon`, `authenticated`, `postgres`, and `service_role`; only the database-owner role had CREATE. No role membership gave `anon` or `authenticated` another effective path. After `REVOKE USAGE ON SCHEMA public FROM PUBLIC, anon, authenticated`, effective `USAGE` was false for both application roles and remained true for `service_role` and `postgres`. Qualified RPC calls failed at the schema boundary, including existing response mutation and new bulk assignment, Communications, CSV import, project-photo, and volunteer-away functions. A local PostgREST volunteer-away POST returned a schema-permission error. All four pending migration files were inspected: none grants schema `USAGE` back. Thus the same gate covers their new RPCs after each migration, provided the live catalog and migrations match the reviewed source.

[PostgreSQL cautions](https://www.postgresql.org/docs/18/ddl-priv.html) that revoking schema `USAGE` alone is not a complete block for existing sessions that already looked up an object. Therefore the gate also requires a controlled recycle of **idle** application database sessions after revocation. In local Supabase, the warmed PostgREST connection ran as `authenticator`; terminating the pre-revoke backend caused a brief HTTP 503 while it reconnected, then the same local RPC returned a schema-permission error. The original backend PID was gone. The existing prepared-statement probe also failed closed, but that one case does not override PostgreSQL's warning. No production session termination is authorized by this document; a fresh live role/session inventory must identify all application connections and reject unknown or active writers before any separately approved recycle.

Local PostgreSQL full custom-format dump, `pg_restore --list`, and globals dump using `postgres` succeeded while restricted; the temporary synthetic archive was removed. A statement prepared as `anon` before the revoke also failed with `permission denied for schema public` when executed in that same already-open session after the revoke. The freeze persisted across independent connections; a transaction rollback left the original ACL unchanged. An independently connected restore command returned the exact same normalized schema grant entries. Every public function ACL, public table ACL, and the reviewed `service_role` function count matched before and after. PostgreSQL may reorder its ACL array entries, so compare grants by grantor, grantee, privilege and grant option—not raw `nspacl::text` order. The disposable local database was restored to normal permissions and stopped.

This restriction also blocks normal application **reads** during maintenance. Because local PUBLIC schema `USAGE` was shared, eight platform roles (`authenticator`, `pgbouncer`, and six `supabase_*` administrative roles) also temporarily lost access to `public`; `service_role` and `postgres` retained their explicit access. The local Auth health endpoint returned 200 while restricted, but this does not prove every platform operation remains available. The live role/ACL topology and platform-service impact must be checked before use. Vercel protection is an additional ingress barrier, not evidence that all database writers are stopped: eligible Vercel users and bypass links can reach the application, while direct Supabase calls bypass Vercel. The schema restriction covers those callers only when they use `anon` or `authenticated`. It does not block `service_role`, `postgres`, Supabase-managed Auth/session writes, or external background workers. No automatic welcome/schedule send, photo upload, or real email is authorized.

## Failure and interruption rules

- A failed checkpoint guard: remove only the unstarted temporary task and STOP. No migration or ACL change.
- Checkpoint/artifact/restore or fingerprint failure: leave database ACL normal and permanent task Enabled/Ready; restore the original Vercel setting only after the safe resting state is verified. Do not retry the checkpoint without authorization.
- An uncommitted ACL transaction rolls back automatically. A committed freeze survives operator-process loss; a new operator must inspect the saved ACL manifest and live state before any restore. Local rehearsal proved this across independent connections.
- A freeze/session-recycle verification failure: do not migrate. If the pre-migration database and lock remain unchanged, restore only the exact snapshotted schema grants, verify normalized equivalence and all object ACL hashes, then STOP. A brief PostgREST reconnect error is expected locally, but a persistent service error or lack of confirmed schema denial is not a passing gate.
- A migration, lock or recovery failure: keep the app gate and permanent task in the runbook-defined safe state; do not reopen app writes or perform a SQL downgrade. Follow the independently proven encrypted recovery procedure if required.
- A final permission restoration mismatch: keep Vercel protection; do not deploy/open traffic until the exact grants are reconciled. Never broaden `service_role` or PUBLIC function EXECUTE to make a check pass.

The schema restriction is suitable for the reviewed normal Project Local app roles **only if** a fresh read-only live inventory confirms the local privilege topology and the owner confirms no external service-role/postgres writer will run. It is not a universal database read-only switch.
