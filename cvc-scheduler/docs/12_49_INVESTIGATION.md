# Project Local 12.49 investigation (local, 2026-09-30)

This is the pre-implementation audit. "Confirmed" means the current repository or an executed check demonstrates the finding; production incident causes remain hypotheses without live traces. No production data or delivery was changed.

## Baseline and architecture

- The tracked tree is clean on `codex/volunteer-home-schedule-polish`; unrelated untracked preview/release-check artifacts are preserved. `origin/master` is `80203cb77ecd3c02427888958d10d62dd0a6a5f7`. The latest production release evidence says 45 migrations through `20260927120000`, with the Task Details release and subsequent volunteer-home frontend deployed. This is documented evidence, not a fresh database query. Local Docker is unavailable at audit time.
- `volunteer_profiles` are workspace-scoped records with UUID identities. A shared contact is not constrained unique in that table. Public lookup goes through `/v/lookup` to `verify_volunteer_schedule_lookup` and issues a volunteer-specific schedule token. It uses a serialized global/name HMAC attempt limit. Personalized links use `volunteer_schedule_access_tokens`. Administrative writes and reads use grants/RLS or authorized RPCs.
- Calendar items have `start_date`, nullable `end_date`, local `start_time`/`end_time`, timezone, lifecycle and draft/published state. Assignment/response state lives in separate tables. Quick View reads published operational projections and must retain its instruction redaction. Notification preparation/claim/finalization lives in database RPCs, with assignment and communication ledgers; the provider dispatch uses a distinct recipient and scoped schedule link.

## Findings by workstream

| Workstream | Confirmed finding | Unresolved point / security implication |
| --- | --- | --- |
| Shared contact lookup | The lookup normalizes email case/edge whitespace, verifies surname and contact, and fails closed if two matches occupy the same workspace. It does not choose the first row. Distinct surnames sharing an email should each match in this code path; the reported failure is not reproduced. | The reported record may have surname, readiness, lifecycle or stored-contact differences. A surname plus shared email does not authenticate an individual household member. A shared phone also lacks individual proof. The safe fallback is a pre-issued individual link or administrator recovery; any new public selection by name would weaken access. |
| CSV identity | `matchVolunteerCsv` treats email or phone as an identity match; duplicate contact rows become ambiguous, and a supplied ID absent from the current workspace becomes ambiguous. The database RPC also rejects any other profile with the same email/phone. | Generated external UUIDs cannot establish a match to internal UUIDs. Automatic contact matching can overwrite another person. Existing ambiguous history must stay untouched. |
| Communications | `communication_recipients` has `unique(operation_id,email)`. Server preview and claim explicitly exclude shared emails. The authoritative initial-assignment ledger is keyed by assignment, while communication recipients are keyed by volunteer and operation. | Removing the email collision requires the preview, claim and unique constraint to change together; provider idempotency must remain recipient-specific. Eligibility reasons are present but exposed as raw codes in the UI. |
| Publishing | Draft/private versus published/live is an explicit admin and volunteer authorization boundary in the 12.19 migration, read models, Quick View and notification SQL. Saving does not send email. | Removing publication in one UI component would leak old drafts or break access. Requires an intentional staged compatibility migration and all projections/notifications reviewed together. Historical drafts must be classified before automatic publication. |
| Overnight | The schema already has `end_date`, but timed items require it to be null and `end_time > start_time` in SQL and TypeScript. Current edit RPCs have no end-date parameter. | Recurrence, conflict, calendar, volunteer, Quick View and email projections use start-date/same-day assumptions. This is a cross-system interval change, not a security-only UI toggle. |
| Performance | Prior release records observed 2–5 s admin navigation and a reported busy-month incident; no production trace or query plan establishes a cause. Local Docker is unavailable. | Supabase saturation, a render loop and query inefficiency remain hypotheses. No performance change is justified without request/query measurements. Loading/error paths need independent review. |
| Release | Repository has 45 ordered SQL files. The backup contract allows the reviewed 43→44→45 transition and final lock; `task-details-release-contract.mjs` pins that old exact release and will fail on any 12.49 migration. The scheduled task currently reports Ready. | Fresh production migration ledger, lock value, most recent encrypted artifact and restore applicability are not yet verified. A new migration requires a reviewed adjacent backup-lock contract and production gate, not reuse of the old release SHA. |

## Sequence and test requirements

1. Correct CSV contact-as-identity matching and the database revalidation in an additive migration. Test synthetic shared contacts, authoritative IDs, duplicate rows, repeat imports, wrong workspace, stale edits and concurrent operations.
2. Remove communication email-as-identity collisions only with recipient-scoped ledger, preview, claim and non-delivering dispatch tests. Preserve per-assignment initial-send reservation, retries and welcome/schedule policies.
3. Make public lookup fail closed for shared contact ambiguity, keep individual links/phone path where genuinely individual, and test attempt limits and enumeration boundaries. Do not claim the historical symptom fixed until reproduced with its actual data shape.
4. Design and implement a staged publication transition, preserving old draft privacy and Quick View redaction; verify save/send/resend and parallel claims.
5. Extend timed intervals through schema/RPC/types/forms/read models and all projections; verify cross-midnight, recurrence, conflict, DST and messages.
6. Measure synthetic busy calendars and real traces before narrow performance changes; then validate migration sequence, backup transition and full cross-feature/security/browser/build gates. Production migration/deployment requires a new preflight, naturally occurring verified backup, exact fingerprints and explicit approval.
