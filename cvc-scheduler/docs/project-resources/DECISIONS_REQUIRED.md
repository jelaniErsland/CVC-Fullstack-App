# Decisions for the simplified architecture

Only four owner decisions remain before implementation planning is finalized. Recommended defaults are explicit proposals; the prior eight-decision document is retained in Git history at `edd1114`.

| ID | Proposed choice | Alternatives and tradeoffs | Approval needed |
| --- | --- | --- | --- |
| D1 — editors | Use current `tasks.edit` for preset text and `calendar.edit` for occurrence text and project-map management, always scoped to an active workspace. | A new `project.map.edit` capability narrows map management but adds grant migration, provisioning and testing. Role titles alone are insufficient. | Confirm which existing project contacts may replace/remove a map, and whether `calendar.edit` is an appropriate authority. |
| D2 — access duration | Let an active/ready verified project volunteer open the current site map even after their last assignment, until profile or workspace access ends. Details remain scoped to that person's currently authorized assignment. | Require a current assignment for map access: narrower but blocks volunteers preparing before work or reviewing directions later. | Confirm whether map access should outlive an assignment while project verification remains valid. |
| D3 — text history | Copy approved preset text into each new occurrence; preset edits never silently change saved items. Explicit edits to a published item keep a prior-text audit revision. Existing notes stay as written and blank old items stay blank. | Live inheritance is less storage but can change instructions without a deliberate publication step. Bulk backfill is faster but may expose unreviewed old descriptions. | Approve snapshot/no-auto-backfill policy and retention for prior published wording. |
| D4 — actual map and recovery | Use a reviewed, approved site-map file and PostgreSQL bytes if its real size, format, legibility and restore tests support this. Set the upload cap from that file and measured headroom. | A large map may require private object storage, extra credentials and a separate encrypted object backup; public URLs are unacceptable. | Provide/identify the exact approved map and written directions; confirm replacement authority, backup retention/capacity and the result of the disposable restore before uploads are enabled. |

No Belgrade invitation extraction, multiple-document publication, security-account model, extra email link scheme or general resource-library policy is needed for these two features. The supplied private map PDFs were not present in this workspace; filename and date alone cannot establish which map is approved. The earlier source-analysis framework remains accessible at `edd1114` if that broader project is ever reopened.
