# Independent encrypted map recovery — minimal extension

The existing scheduled native PostgreSQL backup produces an age-encrypted six-member package, keeps 14 daily and 8 weekly generations, uses a separately held recovery identity, and is restored under the current runbook. Do not start, change or reconfigure the production task during architecture review. Existing production photo uploads remain disabled; a successful restore of empty Storage metadata is not proof that actual files recover.

Under the recommended small-map **PostgreSQL bytea** design, the new `workspace_site_maps` rows include both map metadata and bytes. Native schema/data dumps therefore capture both in the same encrypted database snapshot; no second object-storage provider, object-backup job or managed backup tier is needed. Include any approved retained prior map version rows and the small instruction-history table. Update the backup's exact table/migration inventories and restore assertions only during an implementation stage. Preserve its lock, DPAPI connection secret, age encryption, plaintext cleanup, schedule, failure notification and independent destination. No database-only status may be called complete for maps unless the map byte checks below pass.

For each workspace/version in the snapshot, compute a manifest entry with opaque workspace/version IDs, MIME, byte count and SHA-256 of **the stored bytes**. Put detailed entries inside the encrypted package; external status contains only aggregate counts, age and safe failure codes. Verify the dump and encrypted archive checksum using the established procedure. If any map row is missing its bytes, has a mismatched hash, fails the tested map-size bound, or is omitted from the dump, mark that backup generation incomplete, retain the last good copy and signal failure through the existing safe channel. A removed map's tombstone and retained versions follow the agreed retention policy; previously downloaded copies cannot be recalled.

**Enablement gate:** after the code and any narrow migrations are reviewed, create a nonproduction fixture with two projects, each with different synthetic map bytes and metadata. Capture using the intended encrypted backup path, then restore into fresh disposable infrastructure with no email transport or public endpoint. Compare table counts and SHA-256 bytes for both projects, verify the current version/tombstone pointer, and attempt authorized and forbidden retrieval with real local volunteer sessions (including same-household and cross-project cases). Include replacement, removal, one deliberately corrupted/missing byte sample, bad key, interrupted package and stale backup scenarios. A complete restore passes only when byte hashes, metadata, grants/RLS and delivery boundaries match. Record artifact generation, recovery key custody confirmation and observed restore time without committing private data.

When a map is replaced, keep enough approved prior versions to support the established retention and audit decision; avoid unbounded database growth. The owner decides whether retained versions expire with 14 daily/8 weekly backups or remain longer. A removal denies current access immediately, but encrypted retained backups still contain old bytes until their normal expiry. A restore to an older point must apply later removal/revocation decisions or leave map delivery disabled until reconciled.

**RPO/RTO:** the existing daily schedule implies up to roughly 24 hours of unsaved map changes between good backups; this is a proposed acceptance target, not zero loss. Restore time must be measured during the disposable drill. Monitor scheduled backup success, artifact age, map-row/hash coverage, encrypted size growth and available independent storage. A new map can materially enlarge every retained dump, so inspect the actual approved file and existing OneDrive capacity before enabling uploads. For example, one 8 MiB map per 10 projects across 22 full backup generations is roughly 1.7 GiB before compression or other data; this is illustrative, not a promise about the actual file.

If the real map forces an object-store design, database-only backup becomes insufficient. Return with a separately approved manifest and encrypted object-copy/restore design; do not enable that storage until a full disposable byte restore passes. The default PostgreSQL design has no new storage subscription, subject to actual database capacity, existing backup space and processing limits. No production backup run is required for this architecture decision.
