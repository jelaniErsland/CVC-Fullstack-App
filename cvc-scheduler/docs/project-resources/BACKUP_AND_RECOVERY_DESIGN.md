# Independent encrypted backup and recovery — proposed extension
**Storage enablement gate:** a database-only restore is not success for this feature. No production bucket/upload/publish is enabled until a complete disposable metadata-plus-object restore passes.

## Existing system to preserve
Current native PostgreSQL backup script produces roles.sql, schema.sql, data.sql, two migration files and manifest.json, encrypts with age before persistent OneDrive storage and writes safe status. Existing task uses daily 03:15 local scheduling, 14 daily/8 weekly retention, production/project/migration locks, DPAPI-protected connection secret, duplicate prevention, cleanup and failure notification. Its private recovery key is separately held, not needed by the backup writer. Historical docs contain older migration/tool references; CURRENT_STATE and current script govern. No task was started or altered in this architecture stage.

12.47 restored application data, essential Auth users/identities and current empty Storage metadata on a compatible isolated platform. It did not prove nonempty BLOB recovery, live session restoration or provider configuration restoration.

## Concrete v2 design
Extend the reviewed pipeline with a versioned **complete-feature generation**, retaining v1 database evidence compatibility. Each v2 self-contained encrypted archive contains the database package plus `objects/`, a confidential resource-index manifest and verification summary. Existing six-member validators must explicitly recognize v2; never append files while still labeling the package v1.

1. Acquire one backup generation lease and physical-object-purge lock; ordinary reads/uploads/publication continue. Resource objects are immutable. Any deletion worker must honor this lock/pins.
2. Establish one repeatable-read exported PostgreSQL snapshot. Derive the required version set and related DB metadata from that same snapshot; use compatible native dump invocations sharing it. Freeze DDL/migrations during capture under the established release procedure. Validate actual pg_dump/snapshot behavior locally before adopting; today's separate dumps must not be assumed transactionally identical.
3. Required objects include current published versions, unexpired/past instruction snapshot references kept for audit, retained superseded/revoked versions, approved derivatives and retained original sources. Quarantine drafts can be excluded only under an approved short expiry policy and explicit manifest declaration. No excluded object may be referenced by a published revision.
4. Read required objects through a dedicated read-only bucket credential, from exact manifest keys only. Verify byte count and SHA-256 on full read, not ETag alone. Missing, substituted, partially read or hash-mismatched object fails **complete-feature** backup.
5. Manifest fields: format/generation ID, DB snapshot boundary, capture times, schema terminal, tool versions, resource/version/workspace opaque IDs, exact object key/variant, MIME/bytes/SHA-256, classification, retention/deletion state, original-to-derivative relationship and file membership checksums. This detailed inventory is itself sensitive: include it only inside encryption. Public status exposes aggregate success/failure/age/size/checksum and safe codes, no document titles, people, tokens or object URLs.
6. Stage plaintext only in restricted temporary storage outside repo/OneDrive. Encrypt the complete package to the existing approved public age recipient, independently checksum encrypted output, atomically publish only after all steps pass. Key custody/rotation/recovery copies retain existing guarantees.
7. Record complete-feature success and release pins. On failure, keep last successful generations and send the existing safe failure signal; cleanup and pin expiry are crash-tested. A DB-only success may still be retained and labeled DB-only, but cannot make complete-feature status green or advance its retention watermark.

Proposed RPO: up to 24 hours under a functioning daily task; stale complete-feature status after 26 hours raises an operator alert. This is not zero-loss between backups. New uploads may be published under that accepted RPO only after storage recovery is operational; no automatic manual backup invocation on every publication. RTO target: four hours for the small reference corpus after credentials/platform are recovered; this is a drill target, not a proven promise.

## Retention and deletion
Retain self-contained complete generations with the existing 14 daily/8 weekly policy. Count/purge only recognized complete generation files; never delete the last good complete copy after a partial run. Metadata and bytes share retention. Proposed superseded resource retention: through last pinned assignment history or 90 days after project close, whichever later, subject to owner approval; this is a product retention choice, not a legal requirement.

Revocation removes current access immediately but does not erase encrypted historical backups. A pending purge tombstone records resource/version ID and effective revocation; deletion is delayed until no required snapshot reference or backup pin remains. Emergency redaction requires revoke first, new sanitized version second, and documented backup retention treatment. Do not promise immediate erasure from retained immutable encrypted generations. On restore, reconcile the separately preserved latest revocation/tombstone register before serving anything. If it cannot be trusted, leave restored resources disabled until coordinator re-approval.

Full packages avoid a fragile shared-blob deduplication/garbage-collection dependency. At larger scale, content-addressed encrypted blob packs and manifests could reduce storage, but that is a separate reviewed design, not hidden complexity in V1.

## Restore procedure and verification
Restore into fresh disposable infrastructure with no email transport, no public endpoints and no connection to production. Bootstrap compatible Auth/Storage definitions as in the current runbook; restore roles conservatively, schema/data/migrations under reviewed ACL handling. Do not blindly replay managed platform owners or broaden grants.

Restore resource objects into new private buckets under exact immutable keys; verify every required object hash/size. Recreate bucket credentials/policies through separately held administrative custody, not from committed secrets. Restore metadata pointers only after all objects validate, or keep resource feature disabled until reconciliation completes. Verify all workspace/version/reference FKs, exact capability/RPC/default ACL policy, no public bucket access and no cross-project delivery. Apply current revocations; reissue credentials after platform recovery rather than pretending old browser sessions survive.

Drill fixtures: two workspaces and shared-household people, published/general/restricted versions, replaced and revoked files, missing and altered objects, scanner derivatives and accessible summaries, cancellation/reassignment, concurrent replace/purge during capture, provider interruption, interrupted encryption/atomic publish, key rotation, wrong migration lock, inaccessible key, exhausted temporary disk and stale scanner/backup state. Validate a volunteer's authorized byte hash and forbidden guessed-ID retrieval after restore. Demonstrate one inaccessible private source stays inaccessible. No live source PDF needed for these tests.

An operator review record includes elapsed restore time, manifest validation, object count/bytes/hashes, authorization results, safe status/failure notification and complete cleanup. Failure of any object or isolation check blocks storage enablement. Monitor object coverage, last complete generation age, failed captures, restore age, quota growth and review-due resources.

## Cost model and approval
Rates checked from official pages on 2026-09-26; budget is illustrative, not an account quote.

- Supabase Free currently lists 1 GB files and 5 GB uncached egress; Pro starts at $25/month with 100 GB files and 250 GB uncached egress, then $0.0213/GB storage and $0.09/GB uncached egress. Existing plan/other usage is not inspected. [Supabase pricing](https://supabase.com/pricing)
- R2 Standard lists $0.015/GB-month, $4.50/million Class A and $0.36/million Class B operations, with monthly free allowances of 10 GB, 1 million A and 10 million B; internet egress is free. Account eligibility and other usage matter. [R2 pricing](https://developers.cloudflare.com/r2/pricing/)

Reference workload: 10 projects × 20 documents × 2 retained versions × 2 MiB = about 0.78 GiB before derivatives/originals. Allow 2 GiB total source storage and 2,000 monthly 2 MiB views (~3.9 GiB delivery). R2 storage/operations could fit free allowances; 22 full 2 GiB backup copies consume about 44 GiB of existing independent storage. No extra backup subscription is assumed if existing capacity covers it. Network retries, derivative tiles, quarantine and historical growth must be measured.

A larger 20 GiB retained corpus costs about $0.15/month R2 storage beyond its 10 GB allowance, before operations; 22 full generations need ~440 GiB backup space. This makes retention/capacity review material even when source storage is cheap. Existing OneDrive capacity and plan price are unknown; owner approval is required for any capacity purchase. Application gateway bandwidth/compute also consumes existing Vercel quota.

Scanner/processing compute is the main likely incremental cost: budget **$5–15/month as an engineering allowance**, not a verified vendor quote, or an owner-operated isolated worker with no new subscription but more maintenance/downtime. Select and price the worker before implementation. Small deployment planning range: **$0–15/month incremental**, conditional on current hosting/backup quotas and worker choice; paid Supabase alternative may add at least $25/month if upgrading is necessary. No managed PITR or expensive backup tier is required by this proposal. Owner approves vendor, operator and monthly cap before any provisioning.
