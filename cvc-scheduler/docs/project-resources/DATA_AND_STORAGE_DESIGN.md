# Data and storage design — proposal only
No DDL, bucket or route is created. All new names are proposed contracts. Existing workspaces, volunteer profiles, contacts, task presets, Calendar items, assignments and response ledgers remain authoritative.

## Storage alternatives and recommendation
| Option | Security/revocation | Cost/operations | Assessment |
| --- | --- | --- | --- |
| Private Supabase Storage + existing Auth RLS | Natural for contact JWTs; volunteer bearer is not a Supabase user JWT. A trusted broker is needed for volunteer reads. Service keys bypass RLS and would be a new exception to this app's no-service-role runtime boundary. | Same vendor; current production object recovery is unproven. Billing may force a plan upgrade. | Viable alternative if a least-privilege broker/credential design is approved. Do not reuse the local photo adapter. |
| Private Cloudflare R2 + Supabase metadata/RPC authorization | Bucket-scoped credentials separate object access from database privileges. No public domain/bucket. Every download passes application authorization; storage itself cannot interpret volunteer grants. | Additional vendor/credential recovery; low storage/egress cost, still requires scanner and independent backup. | **Proposed D7 choice:** two private buckets, quarantine and approved versions; no Supabase service-role credential added to product runtime. |
| Permanent public storage URLs | Anyone with URL can retrieve; no per-volunteer revocation. | Simple, inappropriate for this feature. | Rejected for every resource class. |
| Short-lived signed GET | Authorize before issuing, but recipient can forward/reuse until expiry; may bypass later revocation for that interval. | Efficient direct downloads; large files easier. | Defer for restricted files. Optional future general-document optimization only with explicit acceptance of residual access window. |
| Server-authorized content gateway | Fresh decision on every request/range; no reusable object URL sent to browser. Downloaded/in-flight bytes still cannot be recalled. | Application bandwidth/compute and platform body limits. | Proposed default for all classes, with bounded first-release file sizes. |

Supabase documents private storage RLS and the elevated service-key bypass: [access control](https://supabase.com/docs/guides/storage/security/access-control). Private downloads can use authenticated or signed retrieval: [serving assets](https://supabase.com/docs/guides/storage/serving/downloads). This proposal chooses application-mediated reads to keep revocation tied to live project/assignment state.

## Proposed entities
All IDs are opaque UUIDs. Every child carries workspace_id and composite foreign keys to its parent workspace; globally unique IDs alone are not enough. Server mutation RPCs use existing verified contact context and optimistic expected revision, with least-privilege execute ACLs and pinned empty search_path.

| Entity | Principal fields / relationships |
| --- | --- |
| project_information_revisions | id, workspace_id, revision, structured sections, state draft/published/superseded, created_by, approved_by, published_at, reviewed_at, expected prior revision. A workspace has one current published pointer. Empty fields omitted from volunteer DTO. |
| task_instruction_revisions | id, workspace_id, task_preset_id, revision, typed instruction fields, reporting contact projection reference, draft/approved state, audit actor/time. Does not contain assignment dates or volunteer lists. |
| calendar_instruction_revisions | id, workspace_id, calendar_item_id, source_preset_revision_id nullable, explicit field override modes, resolved immutable content, revision/state/audit. One current published pointer per item. Historical revisions append-only. |
| project_resources | id, workspace_id, title, description, audience_class, lifecycle draft/published/unpublished/archived, current_version_id, owner_contact_id, review_due_at, concurrency version. Classification belongs to resource and cannot be lowered through a reference. |
| resource_versions | id, resource_id, workspace_id, version_number, processing_state, source_object_key (private admin metadata), approved object key, SHA-256, bytes, canonical MIME, page/dimension metadata, accessible summary, scan result/version/time, source approval record, created_by. Immutable validated objects. |
| resource_attachments | workspace_id, resource_id, exact resource_version_id and exactly one typed parent revision FK (project info / preset instruction / Calendar instruction), display order, optional narrowed audience. Explicit XOR/check constraints; no arbitrary polymorphic table name. |
| resource_access_grants | workspace_id, grantee volunteer_profile_id or contact_id, class/resource scope, optional exact calendar_item_id, valid_from/until, approved_by, reason code, revoked_at. No email grants or wildcard cross-workspace grants. |
| security_identity_bindings | workspace_id, volunteer_profile_id/contact_id, verified auth_user_id, verified_by/time, assurance requirement, revoked_at. Optional C4 phase only; individual binding is not inferred from email. |
| resource_audit_events | workspace_id, actor reference, resource/revision/version, action, timestamp, request id, old/new classification and version hashes; append-only. No document body, private contact values or raw credentials. |
| resource_upload_intents | workspace_id, resource_id, random quarantine key, bounded type/size, creator, nonce/expiry/state; replay-safe finalize. Scanner state and failed validation retained briefly for operations. |
| resource_backup_runs / resource_backup_pins | opaque generation, state, snapshot boundary, version IDs pinned against physical purge, completion/integrity attestations; operator-only. No storage secrets in DB. |

These suggest about 12 new tables (including the optional security identity binding and two backup tables) plus published-pointer indexes/constraints and narrow RPCs; final split depends on SQL design review. Do not add all fields to existing Calendar/preset tables indiscriminately. A resource may attach to several instruction revisions in one workspace. No cross-project sharing in V1: an approved copy is a distinct resource and review.

## Object lifecycle
Object keys: private quarantine bucket `uploads/{workspaceUUID}/{intentUUID}/{randomUUID}`; private approved bucket `workspaces/{workspaceUUID}/resources/{resourceUUID}/versions/{versionUUID}/{variant}`. No names, email, source filename or authorization token in keys. Variants include approved.pdf, display.webp and map page/tiles where applicable. Keys are server-generated, immutable and never reused. No public bucket, r2.dev or public custom-domain delivery.

Admin upload initiation checks workspace/edit/class authority and CSRF. It creates an expiring intent and a short-lived signed PUT for one random quarantine key (proposed five minutes). Direct upload avoids the application request-body limit. Browser size/MIME is advisory; finalize rechecks stored byte size and sniffed format. A signed PUT may be reusable before expiry, so scanning copies a checksum-verified generation to a new immutable approved key; never publish the mutable quarantine key. Final publication verifies the processed hash and intent state again.

Proposed source limits: PDF up to 20 MiB and 100 pages; still JPEG/PNG/WebP up to 6 MiB and 24 megapixels; no SVG, HTML, ZIP, office files, encrypted PDF, attachments, forms, scripts, launch actions or embedded remote content. Validate magic bytes, file structure, decompression/CPU/memory budgets, page count, malware scanner result and content-disarm policy. An isolated asynchronous worker performs scanning/re-encoding without network fetching from document contents. Scanner unavailable/stale definitions/timeout means not publishable. Malware scan is risk reduction, not a guarantee; keep parsers patched and sandboxed.

Use separate bucket-scoped credentials for upload/scanner, content reader and backup reader; verify actual provider permissions before implementation. Do not claim key-prefix IAM scoping if provider only supports bucket scope. The runtime reader is read-only on approved objects, never on quarantine. Scanner is isolated from production DB secrets, backup secrets, age identity and email transport. An owner-operated worker in a disposable sandbox is a cost option; a dedicated small worker is the operational default proposal pending price/owner approval. It is not the backup task.

**Delivery size gate:** Vercel documents a 4.5 MB Function request/response payload limit ([limits](https://vercel.com/docs/functions/limitations)). Proposed V1 approved PDF/download variants are at most **3 MiB**, images 2 MiB; map tiles/page images at most 1 MiB, with individually authorized requests. Original uploads can be larger but cannot publish unless a readable, accessible approved derivative meets these limits. Never silently downsample a map until labels are unreadable. If the real source needs a larger full-file download, either approve a dedicated streaming gateway and revised cost/identity design or defer that file; do not assume streaming escapes platform limits. This decision is blocked on actual source size/legibility. Originals remain restricted retention material, not volunteer downloads.

## Proposed endpoint contracts
- Admin POST upload-intents/finalize: authenticated contact, capability and intended class, same-origin/CSRF, bounded request, idempotency key. Response contains only short-lived upload target and intent ID, never a broad credential.
- Admin GET validated preview: draft-view capability plus scan-clean exact version. Audit preview access to C4 without logging content.
- Admin POST publish/replace/unpublish/archive: expected revision and reviewed impact fingerprint; transactional metadata pointer/audit change after object exists/hash matches; forbid broadening referenced audience silently.
- Volunteer GET /v/project-information and /v/resources/{id}: use existing /v cookie path; return authorized DTO only. Admin equivalent uses verified contact context.
- GET /v/resources/{id}/versions/{version}/content (and admin equivalent): authorize requested exact version/variant against current resource state and attachment/grant. Fetch only a server-derived object key. Support bounded Range/HEAD with the same checks; reject multipart/oversized ranges. Content-Disposition uses sanitized title, nosniff, private no-store, no-referrer, noindex and restrictive CSP. No CDN/service-worker caching, ETag reuse across users or public thumbnails. App route errors do not expose storage keys.
- C4 read also verifies current individual Auth identity/assurance and scoped grant. Neither browser-submitted auth level nor schedule token suffices.

Unauthorized and unknown identifiers receive equivalent 404-style output and no sensitive title. Authorized missing object gives a safe temporary-unavailable state and bounded internal failure code. Logs contain request correlation, safe event code and opaque audit ID only; never token path/query, source document body or contact values. Inspect platform/proxy logs too: app-level redaction alone cannot erase upstream URL logs.

## Version and revocation rules
Publishing/replacement requires class approval and exact source/derivative review. Immutable snapshots pin exact versions. A revoked resource/version is denied despite historical attachment. An eligible current version may be offered only after fresh authorization; no automatic cross-audience redirect. Archive/unpublish denies volunteer listing and bytes; physical deletion waits for references, retention and backup pins. Ordinary admin editors cannot purge. Restores must replay revocations made after the chosen snapshot before access resumes.

A downloaded PDF or screenshot is outside technical recall. Minimize original private contacts; display current role contacts in authorized HTML where possible. A “do not share” label is not DRM. C4 export can be disabled in UI by policy but cannot prevent screen capture; approval must account for this.

## DTOs reusable by Batch 3
Proposed read-only `ResolvedAssignmentInstructions`: exact assignment/item reference, authoritative schedule, published instruction revision, safe typed sections, reporting/help contacts with approved channels, authorized ResourceCard[] and project-information link. `ResourceCard` contains resource/version ID, title, purpose, MIME/bytes, review date and allowed actions; never raw object path or grants. `ProjectInformation` contains workspace identity and published nonempty sections. Batch 3 can place this reader in its existing inspector without changing Calendar navigation. Batch 5 consumes only allowlisted deep links and approved public copy; no body/document injection into email.
