# Minimal data and map storage design — proposal

## Current contracts and narrow changes

`task_presets.description` is already nullable text with a 2,000-character create limit and a multiline create field. The current Tasks page has **no general edit RPC or form**: only create, color update and archive. A narrow authenticated `tasks.edit` update of description (and any supported existing editable fields) is needed with expected `updated_at`, workspace/RLS checks and the established conflict response. Call it **Assignment details** in the form; treat old descriptions as unreviewed legacy prose until approved for new schedules. Raise the field limit only if real several-paragraph samples need it; coordinate TS and SQL validation rather than assuming unlimited text.

`calendar_items.schedule_notes` is already nullable text up to 4,000 characters, editable through existing Calendar operations and present in the authorized volunteer schedule projection. Use it as the **resolved item-level assignment details**. On new preset-based item creation, copy the current approved preset text server-side into this field unless the administrator supplied explicit text or intentionally cleared it. The distinction among inherit, replace and clear exists in the form command; the stored result is the plain resolved string or null. Repeat creates independent items, so each occurrence keeps its own value. One-off items write directly. This is a small extension to existing creation paths, not a new inheritance engine.

Existing item notes are preserved byte-for-byte during migration, apart from existing validation/normalization. They do not automatically merge with a preset; show the item text as currently saved. Preset edits leave every existing item untouched. If administrators deliberately update future items, use an exact-item selection and stale-version check. The existing volunteer component currently labels `scheduleNotes` “Notes” and already preserves line breaks; the proposed read-only disclosure replaces that presentation without changing the response model.

**Historical audit:** one small append-only instruction-history table may hold workspace ID, exact preset ID **or** Calendar item ID (an XOR constraint with real FKs), old/new normalized text, actor, event time and expected version. Write it in the same transaction as each successful text edit. This is required to prove prior published item wording after an edit; an `updated_at` timestamp alone does not preserve it. If repository review finds an existing durable row-history mechanism with those guarantees, reuse it and omit this table. No separate resource, attachment, audience or security-grant tables are proposed.

## One map per workspace

**Recommended default:** store the approved map's bytes and metadata in PostgreSQL, under a private workspace-scoped table, because the application already has a native encrypted database backup and there is only one map per project. Proposed table: `workspace_site_maps(workspace_id PK/FK, current_version, original_name_display, media_type, byte_length, sha256, approved_bytes bytea, accessible_directions, reviewed_at, updated_at, updated_by, removed_at)`. Keep one previous approved version temporarily during replacement until the new version validates; a small related version table is acceptable if transactional replacement and history cannot be handled safely in one row. Original filenames are display metadata only, never storage paths or authority. The schema and exact retention remain for implementation review.

There is no production-ready photo object adapter. `lib/projectPhoto/files.server.ts` is deliberately loopback-only and refuses Vercel. Do not use its `.local/project-assets` directory for maps or infer that project-photo BLOB recovery is operational.

Database storage is recommended **only after inspecting the actual approved map**. Determine its media type, page count, dimensions, accessible directions and original byte size; then set a cap above that real need with tested headroom. Limit accepted formats to validated PDF, JPEG, PNG or WebP. Reject active PDF content, embedded files, scripts, encrypted PDFs, SVG/HTML/polyglots and malformed/oversized image dimensions. Strip unsafe image metadata and preserve legible map labels. Preview processed output before replacement. PDF validation and any rasterization must run with bounded resources; fail closed if validation fails. This is one map workflow, not a general file-processing platform.

The Vercel Function body limit is 4.5 MB ([official limit](https://vercel.com/docs/functions/limitations)). A map larger than a proven safe upload/response path cannot be enabled through that route by merely raising a UI limit. For a suitably small actual map, accept an authorized bounded upload, hash/validate server-side, and commit bytes and pointer atomically. Serve viewer pages/images or bounded ranges from an authorized route; avoid returning a large base64 field in the volunteer schedule JSON. Test server memory, database dump size and map legibility. If the real approved map is too large for this design, bring back a revised private object-storage and independent object-backup proposal for approval. No arbitrary 3 MiB publication rule remains.

**Delivery:** the viewer requests only the current map in the server-selected workspace, with an opaque version used for cache invalidation but never permission. The route reads a fixed column set, enforces the authorization matrix before accessing bytes, supplies safe content type/disposition and no-store headers, and gives a neutral unavailable response after removal. Zoom and pan happen inside the viewer; a text description is offered alongside the graphic. No public URL, service-role credential in the browser or Quick View projection.

The current system uses private Supabase data and RLS; new table policies and narrowly granted RPCs must follow its deny-by-default function policy. Authorized server delivery may require a reviewed read RPC because schedule-cookie volunteers are not Supabase Auth users. Do not grant broad table select or introduce a runtime service-role key as a shortcut. Map admin upload/replace/remove and volunteer retrieval are the only new endpoints. No bucket, quarantine library or signed-download system is in the default design.

## Alternative if the real map is unsuitable for database storage

A private Supabase Storage or bucket-scoped private object store could handle a larger map, but it adds credentials, object validation and independent byte backup/restore. Short-lived signed GETs create a forwarding/revocation window. A server-authorized gateway gives fresher revocation but consumes application bandwidth. This alternative is **not an automatic implementation dependency**; it requires a new review of the actual file and operating cost before adoption. In neither case is a permanent public URL acceptable.
