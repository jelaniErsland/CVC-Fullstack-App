## Product decisions and implementation

- Volunteer access is intentionally lightweight. The public form accepts an email or phone alone. One eligible match opens the schedule; several matches show a tappable **Who are you?** list with name, project, and congregation. A choice is bound to the entered contact and rechecked by the server. This is contact-based access, not strong identity authentication. Anonymous direct table reads remain denied, and administrator login is unchanged.
- A scoped, opaque volunteer bearer is stored in a 30-day HttpOnly cookie. Valid visits to the Project Local home return to that volunteer's schedule. **Switch volunteer or project** returns to lookup; **Forget this device** clears both current and legacy cookie paths. Ineligible, removed, expired, or archived context returns to lookup.
- Shared email and phone values remain valid household data. CSV import matches authoritative internal IDs, not contact details. The recipient-specific communication ledger and duplicate-send guards remain in force. Shared addresses can receive each reviewed volunteer's own schedule message; the prior 12.49 shared-address suppression and surname lookup grants are removed.
- Timed Calendar items now accept an explicit end date. The UI shows the date and suggests the following day for an earlier end clock. The same interval persists through create, edit, recurring creation, and bulk creation. Database checks reject reversed intervals and missing or ambiguous local DST endpoints. Date/Week/Month/List, volunteer schedules, Night Watch, Quick View projections, notifications, and calendar conflict previews use the interval. Conflicts use half-open endpoints, so shifts touching at 5 AM do not conflict or create duplicate assignments. Reminder start time continues to use the project timezone.
- A newly assigned creator draft is published in the assignment transaction. Legacy drafts remain private until explicitly published. No assignment save sends email.
