# 12.47 Auth and Storage recovery contract — local proof, 2026-09-23

This document records an isolated recovery rehearsal of a verified, encrypted **real production backup**. It authorizes no production action. The four 12.47 migrations remain unapplied in production. No production backup, migration, task change, email, deployment, or photo upload occurred.

## Scope and evidence

The source artifact was independently checked against its status SHA-256, decrypted with the existing operator-held age identity, and verified against its six-member manifest. No identity was generated or copied into the recovery package. The disposable targets had no production connection, no Resend or real SMTP, and no published database port. The CLI bootstrap briefly published loopback-only local service ports **before** recovered data was loaded; those services were stopped before import. Restored databases ran with no network or on an internal Docker network. Pinned local versions were Supabase CLI `2.111.0`, PostgreSQL `17.6.1.156` (server 17.6), GoTrue `v2.194.0`, Storage API `v1.67.20`, PostgREST `v14.15`, and Kong `2.8.1`. A trial of GoTrue `v2.196.0` made no schema change and was rejected in favor of the pinned CLI version. This is a proven compatibility combination for this artifact, not an assertion that every later platform version is compatible.

Project Local's essential Auth data is `auth.users` and `auth.identities`. Nine backed-up users and nine email-provider identities restored with matching source-data hashes. All nine application project contacts and nine workspace grants retain their original Auth relationships; orphan and duplicate identity links are zero. The application's login flow requires an existing Auth user (`shouldCreateUser: false`) and a new OTP request. Sessions, refresh tokens, flow state, OTP artifacts, and MFA session claims are intentionally omitted: restored contacts must sign in again. That is a security choice, not loss of the underlying account or grant. No real login link was sent in this proof. Structural Auth eligibility and pinned GoTrue health passed; an end-to-end real-contact login after disaster remains an operator smoke step once separate Auth email configuration has been restored.

The logical database backup does **not** contain Supabase-managed Auth or Storage table definitions. A compatible fresh Supabase platform must create these first. The backup has managed data in an older column shape: seven empty or transient Auth/Storage `COPY` blocks were incompatible with the pinned platform's columns. Essential users/identities were compatible and restored exactly. The current production Storage scope has zero buckets and zero objects. Empty Storage metadata restored on both targets; the pinned Storage API health check passed. The default project hero needs no Storage object and uploads remain disabled. **Storage platform recovery is structurally proven for current empty-object production scope; BLOB recovery remains separately unproven and blocks future photo upload enablement.**

Logical backup data alone does not restore platform configuration. The recovery operator must recreate Auth site and redirect URLs, enabled provider settings, SMTP/email delivery settings, JWT/signing material, Supabase project keys, and application deployment environment configuration from separately controlled records. Verify by comparing safe configuration names, hashes or provider settings without printing values. Do not copy production credentials into an isolated rehearsal. Sessions from the old environment are not promised to survive key/configuration restoration.
